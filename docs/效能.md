# 效能

> 量測數字與最佳化計畫（2026-10-25 從 `進度.md` 搬來）。效能最佳化排在試玩之後（使用者 2026-10-24 決定）。

## 計畫
- 順序：① 跳躍偵測只在往前被擋住時算 ② AI 決策分批（每 2~4 步，移動照常；要檢查出招時機不變）③ 互推最佳化 ④ 都不夠才 C++（GDExtension，CI 與網頁 wasm 都要能編）。
- 不走流場：尋路只占 0.3 ms，`AStarGrid2D` 已是引擎 C++；GDScript 寫全圖 BFS 可能更慢。上千隻怪或改 C++ 時再考慮。
- 還沒量：alex_work 內顯的實際遊戲數字。

## 網頁版跑動被怪群追（2026-10-26，M5、Chrome CPU 降速 4 倍模擬弱電腦）
- 量法：`PERF_QUERY='?perf&seconds=30&horde=60&elites&player-hp=99999&auto-move=1,0'` 跑 `--perf`，CPU 降速用 DevTools 的 `Emulation.setCPUThrottlingRate`（臨時加在複本，沒進 `release.mjs`）；每次地圖上的怪群不同，比較要看每次呼叫 / 每隻移動中的怪的成本，不要直接比 FPS。
- 原地 → 跑動（60 隻）：每步模擬 7.1 → 9.6 ms；移動中的怪 56 → 93 隻（一路叫醒怪群、後面那串一直在追）。增加最多的是 A*（0 → 每步 5 次、+1.13 ms），其餘每段都跟著變重；後面那串在視野外不畫，畫面同步反而 14.6 → 9.0 ms。FPS 不到 60 時一幀最多補 5 步（`max_physics_steps_per_frame`），每步變慢會被放大。
- 處理：遠的小怪降低重新判斷頻率（v0.45.3），尋路每步 −57~66%。
- 跳躍偵測先用分桶的頂面高度排除（`Terrain.may_rise`，結果和 `ground_at` 相同）：要看在哪裡量。上面的跑動路線每次偵測附近平均只有 0.62 塊石台，幾乎省不到；玩家站在西南墓碑林（`player-at=16.5,76`）時附近平均 4.3 塊、全部是跳不上去的墓碑與牆，100% 被排除，每次偵測 11.1 → 8.9 µs（−20%）。剩下約 8.9 µs 是函式本身的固定開銷（正規化、是否著地），跳躍偵測又只占每步 7~9%，所以墓碑區每步總共約省 1.5~2%；計畫 ① 剩下的要從固定開銷下手。量石台塊數要在網頁版開放 `player-at`（臨時加在複本的 `WEB_URL_ARGS`）。

## 實際遊戲（v0.34.0，3070、headless、200 隻醒著的怪）
- 每步平均 4.16 ms、p99 6.22、最大 7.59。怪物更新 1.92（狀態機 0.93、跳躍偵測 0.52、動畫 0.23）、互推 1.50、地形推出 0.60；尋路平均每步只約 0.3 ms（每隻 0.25 秒才重算）。
- 144 FPS 每幀 6.94 ms：平均已超過（離屏 171~182 FPS），問題是 1% 低幀約 110 FPS（剛好跑到模擬步的那幀）。尖峰來自每步固定約 4 ms，不是尋路擠在同一步。

## 網頁版（`release.mjs --perf`：背景 Chrome 960×540、RTX 3070、60 群怪圍過來、原地每 0.5 秒轉身 180°，30 秒）
- 2026-10-26 淡入淡出改用共用材質快取後：平均 58~60 FPS、p99 18~22 ms，超過 33 ms 的卡頓 4~9 次，全部在開場前 3.5 秒內（第一次載入模型與著色器）；同條件網站上的 v0.44.3（舊做法）：平均 57.7、p99 36.1 ms，卡頓 28 次、整局每 1~2 秒一次。
- **2026-10-27 3070 重量（`--perf` 已改 headless、怪 189~248 隻）：只剩 29~33 FPS、p99 41~57 ms、超過 33 ms 的幀 195~532 筆**；v0.48.2（33.3 / 29.2）與加了跑步、火把改動的版本（29.6 / 29.7）一樣，不是那次改動造成的。和上一行的 58~60 差一半，還沒查是 headless 模式、怪變多（原本 60 群）還是這段期間的其他改動；卡頓明細大多是 `other` 20~33 ms（不在模擬與畫面同步裡）。
- 開場前 3 秒的卡頓（50~100 ms）是著色器在遊戲中才編譯（Compatibility 依有沒有被點光源照到分兩個版本，預熱只編到有光的）；預熱改成前半關燈、後半開燈後：超過 33 ms 的卡頓 1 次（有精英怪時開場 0.5 秒一次 92 ms，還沒追），沒有精英怪時 0 次。2026-10-26 M5（ANGLE Metal）跑 8 次以上帶精英怪的 `--perf`，開場都沒有超過 33 ms 的幀，3070 還沒重量。
- **光源與陰影的對照組**（2026-10-27，M5 + ANGLE Metal，預設情境，`PERF_QUERY` 加 `&lights=0` / `&shadows=0`）：
  - 查證：相容渲染器沒開影子的點光源（精英怪、武器、出口都是）在同一次繪製裡算完，每個物件最多 8 盞（`drivers/gles3/rasterizer_scene_gles3.cpp`「Lights without shadow can all go in base pass」）；只有開影子的光（太陽）讓每個模型多畫一次。所以多幾盞精英怪光不會讓模型多畫幾次，成本是每個像素多算幾盞光。
  - 平均 FPS 四種組合都是 60（M5 頂到垂直同步，看不出填滿率差異，要在內顯量）。
  - 卡頓：光源開 4 次裡 2 次各卡一次 91 / 100 ms（陰影開、關各一次），另外 2 次 0；光源關 3 次都 0。樣本太少，**假設**：92 ms 那次和點光源有關（著色器版本？），還沒抓到卡頓明細。
  - 下一步：在 alex_work（內顯）跑同樣四組，比平均 FPS 與 p99；`perf hitch` 明細行（含第一次出現的模型）記下來。
- 2026-10-28 第一次掉武器 / 開寶箱 / 掉金幣卡 60~90 ms：預熱用過的材質在預熱模型刪掉後被 Godot 釋放（`BaseMaterial3D` 依使用數保留著色器），遊戲中第一次出現重編；`WorldView._warm_materials` 整場保留後，`?loot-test` 場景預熱後才編譯的著色器 12 → 0、卡頓 0。找法：效能追蹤看卡頓幀的 `GLES2Implementation::GetShaderiv`，再抓預熱後才 `compileShader` 的原始碼看材質特徵。
- 2026-10-27 影子跟著淡入淡出（抖動影子）：著色器程式 161 → 175（一般繪製 +8、陰影深度 +7）；M5 `--load` 預熱 2.93 / 3.10 秒 → 3.17 / 2.67 秒（第一次 / 第二次開），看不出差別。有一次第二次開 11.92 秒沒重現。Windows D3D11 那台單一程式要 0.7~1.5 秒，+15 個可能多幾秒，要在那台量。
- 網頁版開場載入約 26 秒：編譯約 160 個著色器程式，有幾個一次 0.7~1.5 秒（ANGLE / D3D11），還沒處理。
  - 量法：`node tools/release.mjs --load --godot <路徑>`（第一次開沒有瀏覽器快取、第二次有）。網站有 gzip：wasm 實際下載 10.2 MB、pck 1.5 MB，下載不是主因。
  - 2026-10-26 M5（ANGLE Metal）：第一次 3.5 秒、第二次 3.1 秒（引擎啟動 0.2 → `_ready` 0.7 → 預熱結束）；172 個程式、預熱時 152 個，每個原始碼約 125 KB；一般繪製 68、陰影深度 59、點光源疊加 22、其他 23；等編譯合計 1.1 / 0.8 秒、最慢一個 32 ms。預熱其餘時間是畫那幾幀（Metal 會延到第一次畫才編一部分）。
  - 26 秒重現不出來，推測是 Windows 的 D3D11 編譯慢（還沒證實）：要在 3070 那台跑 `--load`，看最慢的是哪一類程式再決定從哪裡減。關掉發光零件（不吃光）的投影試過，程式數不變（172 → 172~174），不是那裡。
