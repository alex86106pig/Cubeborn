## 各項內容與評估

### 1. 跳躍與翻滾（已決定要做）
**想法**：角色要能跳，能翻滾閃避，翻滾有極短的無敵幀。使用者補充：能跳對玩家很重要，大家都喜歡跳。

**評估**
- 翻滾：現有架構直接做得到（類似盾擊衝鋒的位移，加上無敵計時）。
- 跳躍：模擬層要加入高度與重力，命中判定要考慮高度。**要在多人連線之前做**，因為連線要同步的資料會改變。

### 3. 物品資料格式（已決定先定格式）
- 物品要有唯一編號與固定的資料格式；存檔、連線同步、掉落表、商店都靠編號。
- 做法選項（實作時再決定）：Godot 內建 Resource 檔、試算表匯出、或維持程式資料表。不需要資料庫伺服器。

### 4. 成長與 build 系統
**想法**：天賦、升級、職業、技能、武器技能、甚至接技，都是我會考慮加進去的。

**評估**
- 局外成長已決定方向（帶出遊戲的貨幣買天賦 / 技能、成就解鎖），需要存檔。
- 局內成長目前只有「武器與道具」，是否另有升級 / 技能選擇未定。
- 「接技」與第 6 點的動作系統綁在一起。規模大，拆小步驟做。

### 5. 通用攻擊判定（已決定）
- 玩家與怪物共用一套攻擊判定：範圍形狀、方向、高度、**能不能被格擋**。
- 怪物取消碰撞傷害，全部改成「預備動作 → 判定 → 收招」的招式。

### 6. 玩家攻擊動作
**想法**：玩家操作的角色的攻擊動作我希望可以很流暢且酷炫，目前只有普攻是手揮動一下而已，未來不可能只有這樣。

**評估**
- 目前動作是程式算出的關節角度，做不出複雜連招。
- 選項：Godot 內建 AnimationPlayer / AnimationTree 做關鍵影格動畫、使用現成動畫素材、或加強程式動畫；再加上特效（揮砍弧光、殘影，目前還沒從網頁版搬）、命中停頓、鏡頭震動。
- 建議先用一把武器做出範例，確定做法再推廣。

### 7. 劍盾右鍵：格擋與盾反
**想法**：現在的雛形的劍盾的右鍵太廢了，我想要先至少改成格擋反擊。
- 按右鍵防禦來自前方 75 度角的攻擊，持續 3 秒。
- 極短時間內瞬間防禦攻擊成功的話，會觸發盾反傷害，對前方一定範圍內的敵人都造成傷害。
- 盾牌只能格擋有方向性的投射物或是近戰攻擊；毒霧這種持續傷害、Boss 砸地板、紅圈 AOE 攻擊等先設定不能防禦。

**已完成（v0.18.0）**：使用者決定按一下自動維持 3 秒、格擋時可以移動、拿掉盾擊衝鋒；其餘由 Claude 訂（左右各 37.5°、完美格擋 0.2 秒、盾反 25 傷害 120° / 2.5、冷卻 4 秒、翻滾可提前結束），規格見 `PROJECT_GUIDELINES.md` 15.15。

### 8. 遊戲整體方向（已寫進設計方向）
使用者原話重點：一場一場分開（雨中冒險 2）、每場玩起來像 Minecraft Dungeons、加上 Hammerwatch 2（地下城、角色視野、關卡與場景設計）；怪物像 POE 成群分布並分普通 / 魔法 / 稀有；POE 式格子背包，裝備欄只留武器最多兩把；武器與道具都有白綠藍紫橘；同種同稀有度武器可合成；道具大小代表強度；有角色視野（逃離鴨科夫）；一場約 2 小時；武器殺怪掉、錢開寶箱拿道具（LORT）；盜墓冒險者、第 1 層挖墳去下一層、之後是陵墓（芙莉蓮零落的王墓）；去下一層的事件類似雨中冒險 2 傳送門。

**已回答的細節**（都已寫進 `設計方向.md`）：道具可旋轉、形狀不規則；武器只掉一把、錢共用；合成要同一種；職業不限制武器；挖墳被打不會中斷；事件越久越多越難；視野外完全看不見；不做全場時間難度、改為每層基礎難度＋事件內上升；倒下假死 → 救援 → 屍體裝背包 → 下一層打冤魂復活。

**Claude 的評估與提醒**
- **事件可以無限拖**：開事件後不走能一直賺錢，靠「難度無上限上升」自然限制。要確認難度上升速度讓「多待一下」值得、但「一直待」必死。
- **視野與多人**：已決定每人只看自己的視野，視野外連隊友都看不到；誤傷隊友開啟（已寫進設計方向）。
- **視野外看不見怪物攻擊**：被看不見的投射物打中可能很挫折，實際玩過再調（例如視野外的攻擊在快命中時才出現）。
- **屍體裝背包**：已決定全員倒下就輸（除非有復活道具）；屍體 Claude 暫定占 2 × 3 = 6 格。誤傷開啟後要注意：盾反、爆炸類道具（火藥包、王墓之心）是否也會傷到隊友，做的時候再問。
- **背包大小**：Claude 暫定 8 × 6 = 48 格（見 `道具清單.md`）。
- **道具外觀**：測試期 3D 場景用統一發光物件＋按 Tab 看說明，2D 圖示用程式畫的簡單向量圖；不必每個道具都做 3D 模型與圖示，可以大幅節省工作量。

### 10. 每層不同的「去下一層事件」
**想法**：除了第 1 層之外，接下來每一層一樣也都有為了去下一關的事件，但是既然都已經在地下城裡面了，挖墳就感覺有點怪，我還不確定該換成什麼，可能可以試試看每一層都不同，往惡搞方面前進也可以，但是本質不變，都是要有人能夠抽空去累積 % 數，在累積 % 數的時候什麼都做不了，玩家隨時可以去累積跟隨時取消，但是沒人做就會緩慢掉落 % 數。

**評估**：本質是同一套「定點累積進度」機制，每層只換外觀與台詞，程式成本低。例子（供參考）：撬開石棺封印、轉動生鏽的升降機絞盤、餵飽守門的骷髏狗、幫亡靈樂團演奏完一首曲子。

### 12. 網頁版連線
**想法**：我朋友說 godot 有自己的多人連線方式，是不是能至少讓網頁玩家互相連線?

**評估**：現在用的就是 Godot 內建的高階多人 API（`SceneMultiplayer` + RPC），只是底下的傳輸用 ENet（UDP），瀏覽器不能用 UDP，所以網頁版連不上。Godot 另外有 `WebSocketMultiplayerPeer` 和 `WebRTCMultiplayerPeer`，換掉傳輸層、RPC 與同步的程式幾乎不用改（`net/net_session.gd`）。卡點是**瀏覽器不能當伺服器**，而 GitHub Pages 只能放靜態檔案，所以一定要另外架一台小伺服器：
- A. WebSocket 中繼：所有封包經過伺服器轉送，最簡單；延遲多一段、伺服器要付流量。
- B. WebRTC：伺服器只負責「牽線」（signaling），之後玩家直連；部分網路還要 TURN 伺服器。
- 兩種都要租伺服器（免費方案也有但會休眠）。Steam 版照舊用 ENet / Steam 連線。

**更新（2026-10-24，參考 yang8629/space_rogue_multiplayer 的做法）**：不用自己架伺服器——借 PeerJS 的免費公開配對伺服器（`wss://0.peerjs.com`）只轉送配對訊息，遊戲資料走 WebRTC 直連，和 GitHub Pages 純靜態相容。
- 做法（A）：網頁版的 `net_session.gd` 改用 Godot 內建的 `WebRTCMultiplayerPeer`（RPC、快照、輸入的程式不用改；有 unreliable 頻道）；新增一支配對程式，用 `WebSocketPeer` 連 PeerJS 伺服器收發 OFFER / ANSWER / CANDIDATE / HEARTBEAT。伺服器只原樣轉送，兩端都是我們的程式，不必相容 PeerJS 函式庫的格式，約 150~250 行。連線面板從 IP 改成房號（Peer ID = 前綴 + 房號，撞到 ID-TAKEN 就重抽）。ICE 照抄 PeerJS 預設的 STUN / 公開 TURN（`peerjs / peerjsp`，免費共用、沒有保證）。
- 不走 B（JavaScriptBridge 包 PeerJS 函式庫）：要自己寫 `MultiplayerPeerExtension` 轉封包，比 A 繞。
- ~~網頁版和 Windows 版不能互連~~：v0.40.0 裝了 `webrtc-native` 擴充，Windows 版也能用房號連線、和網頁版互連（IP 連線保留）。
- 風險：① 房主在瀏覽器跑整個模擬，wasm 裡的 GDScript 沒有 JIT、單執行緒，可能比桌面版（200 隻怪每步 4.16 ms）慢好幾倍；② 房主切到背景分頁時，畫面更新停住、模擬也停 → 規定房主不能切；③ 快照約 10 KB，接近 WebRTC 單則約 16 KB 的安全上限，unreliable 不能切段 → 「只送附近的實體 + 二進位」是前置條件；④ PeerJS 公開伺服器偶爾會掛（掛時不能開新房，已連上的不受影響）。
- 順序：① 先量：v0.34.3 起網頁版可以從網址帶參數，推送後開 `https://alex86106pig.github.io/Cubeborn/?horde=200&perf&seconds=20&player-hp=99999`，看瀏覽器 console 的 `perf` 那行；每步邏輯約 8 ms 內才做 ② 快照瘦身（`docs/進度.md` 已知限制那條）③ 做 A。
  - **2026-10-24 已量（3070 桌機、內建瀏覽器、v0.34.3 網站）**：場上 180 隻怪（畫面內 30 隻）每步邏輯 **2.61 ms**、畫面同步 2.38 ms、平均 81.5 FPS、p99 幀 34.7 ms、最慢 99.7 ms、297 次繪製 → **邏輯跑得動**（遠低於 8 ms），瓶頸在畫面（Compatibility 渲染器），FPS 尖峰明顯。同參數桌面 headless 那次場上變成 382 隻（每步 10.6 ms），數量不同、不能直接比。alex_work 內顯還沒量。
  - **v0.35.0 快照瘦身完成**：一般每份 1.7~3.8 KB、身邊 120 隻 7.0 KB（原本約 28 KB）。
  - **v0.36.0 做 A 完成**（
et/peerjs_signaling.gd、
et/net_session.gd）：4 碼房號。還沒在瀏覽器實際連過。

### 13. 程式架構文件與 token 消耗
**想法**：請問你現在各個程式路徑跟分類有整理好嗎? 因為我看你最近改東西都消耗非常多TOKEN，所以我在想有沒有可能是這個問題? 是不是沒有CODE的架構文件? 程式如何分層 程式風格等之類的

**評估**：架構文件其實有：`PROJECT_GUIDELINES.md`（分層 sim / view / ui / net、命名、狀態機、事件、資料格式、連線規範）與 `CLAUDE.md` 的檔案地圖，分層也有自動檢查（sim/ 不能碰節點、輸入、時間）。token 用得多主要是其他原因（2026-10-24 量的檔案大小）：
- 檔案太大：`tests/check.gd` 4004 行、`view/world_view.gd` 772 行、`sim/player.gd` 758 行，每次要找位置就得搜尋、分段讀。
- 文件寫得太密：`PROJECT_GUIDELINES.md` 第 15 節每一點都是一大段；`CLAUDE.md` 每次對話都會整份載入，檔案地圖的每一列很長。
- 截圖很貴：一張 1920×1080 的截圖比讀好幾百行程式還多；量 FPS 被其他遊戲干擾時又得重量。
- 工作本身大：上一輪是 4 個版本一起做。
- 建議做法：(1) `check.gd` 照區塊拆成幾個檔（已有 net_checks、monster_checks 的先例）；(2) `world_view.gd` 把剪影、狀態染色拆出去；(3) 加一頁短的「怎麼新增一把武器 / 一個道具 / 一種怪」步驟說明，之後改東西照著走，不必每次重新找；(4) 精簡 `CLAUDE.md` 檔案地圖，細節移到 `PROJECT_GUIDELINES.md`。

### 14~16. 主選單、單人開始、多人大廳
**想法**：做 MAIN MENU（單人遊戲、多人遊戲、離開遊戲 先做這三個選項）；做單人遊戲（選好職業即可開始）；做多人連線大廳畫面（選擇職業 其他玩家都按準備好後 主機才能按開始）

### 19. 局外成長與登入
**想法**：局外成長要素（但是局外成長要素的話是不是就必須要讓玩家能夠用某種方式登入? ）

**評估**：不一定要登入。
- 桌面 / Steam 版：存檔放在玩家電腦（`user://`），Steam 版再開 Steam Cloud，就會跟著 Steam 帳號走、換電腦也在，不必自己做登入。雨中冒險 2 等合作遊戲都是這樣。
- 網頁版：存在瀏覽器裡（IndexedDB），清掉瀏覽器資料或換電腦就沒了；試玩版可以接受。
- 本機存檔玩家改得到（可以作弊）；合作 PvE 通常可以接受。只有要做排行榜、防作弊、跨平台共用進度時，才需要自己的帳號系統與伺服器。
- 建議：先做本機存檔 + Steam Cloud，存檔格式加版本號，之後要換也換得了。
